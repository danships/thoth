# THOTH-010: Added date column type

# Plan: Add a `date` column type to data sources

## Problem

Data source columns currently support only `string`, `number`, and `boolean`. We need
a new `date` column type so users can store dates/times.

## Decisions (confirmed with user)

- **Single** **`date`** **column type.** Values are **always stored as full ISO 8601 strings**

- **Per-column** **`mode`**: one of `date` | `time` | `datetime`, chosen in the column form.

- **Per-column** **`displayFormat`**: a preset selected from a dropdown, mapped to

- Native inputs give partial values (a `date` input yields `YYYY-MM-DD`, a `time` input

## Design details

### Value schema

- Add `dateValueSchema = { type: 'date', value: z.string().datetime() }` (or a `.refine`
that accepts ISO 8601). Add it to the `pageValueSchema` discriminated union.

### Column schema

- Add `dateColumnSchema = baseColumnSchema.extend({ type: 'date', mode, displayFormat })`
where:

- Add `dateColumnSchema` to the `columnSchema` discriminated union.

### Display format presets

- Create a small shared module (e.g. `src/lib/data-source/date-format.ts`) exporting:

- Example date presets: `'31 Jan 2026'`, `'2026-01-31'`, `'01/31/2026'`, `'Jan 31, 2026'`.
Time presets: `'14:30'`, `'2:30 PM'`. Datetime presets combine the two.

### Column create/update endpoints

- `create-data-source-column.ts` and `update-data-source-column.ts`: extend the body
`type` union to include `'date'`, and add optional `mode` + `displayFormat` fields.
Validate that `mode`/`displayFormat` are present/valid when `type === 'date'`.

- Verify the API route handlers (`.../columns/route.ts`, `.../columns/[columnId]/route.ts`)
persist the new fields onto the stored column object.

### Values API route

- `pages/[id]/values/route.ts` already validates `column.type === value.type`; since a
`date` column ↔ `date` value, this works once schemas include `date`. No structural
change needed beyond the schema update, but re-verify.

### UI — column form (`column-form-modal.tsx`)

- Add `date` to the type `Select` (label e.g. "Date").

- When `type === 'date'`, show two extra controls:

- Extend `ColumnFormValues`, `validate`, and the `useEffect` initial-values sync to
include `mode` and `displayFormat`. Remove/repl. the hardcoded `allowedTypes` list.

### UI — editable cell (new atom `editable-date-cell.tsx`)

- New atom rendering a native `<input type={date|time|datetime-local}>` based on `mode`.

- Value in = ISO string → converted to the input's expected value via `toInputValue`.

- On change/blur → convert back to full ISO via `toIsoFromInput` and call
`onChange(col.id, { type: 'date', value: iso })`.

### UI — data table row (`data-table-row.tsx`)

- Add a branch: when `col.type === 'date'`, render `EditableDateCell` with the column
`mode`; pass through the ISO value.

### UI — read-only display

- Wherever a stored value is shown as text (the editable cell shows the input; any
non-editing/read display path), format via `formatDateValue(...)`. In the current table
the cell is always editable, so the input itself is the display; confirm there is no
other place page values are rendered that needs the formatted output. If the table cell
should show the formatted value when not focused, handle that inside the new atom.

### Plumbing / types threaded through

- `use-create-data-source-column.ts`: widen `type` param and pass `mode`/`displayFormat`.

- `data-view-table.tsx` `handleColumnSubmit`: widen the values type; pass new fields to
`createColumn` / `updateColumn`.

- Any other `'string' | 'number' | 'boolean'` literal unions found (grep) must be widened
to include `'date'`.

## Notes / considerations

- Native `datetime-local` and `time` inputs are timezone-naive; storing full ISO means
choosing a timezone convention. Plan: interpret native input as **local time** and
store as ISO (with the resulting UTC `Z` value), and convert back to local for the
input. Document this in the helper.

- `time` mode needs a date component to form a valid full ISO 8601 string; use today's
date as the reference and only ever display the time part.

- Existing columns without `mode`/`displayFormat` are unaffected (only new `date`
columns carry those fields); no data migration required.
